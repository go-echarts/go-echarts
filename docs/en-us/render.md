# Render

Render is an interface for render charts, alias the `Renderer`.

```go
// Renderer
// Any kinds of charts have their render implementation, and
// you can define your own render logic easily.
type Renderer interface {
    Render(w io.Writer) error
    RenderContent() []byte
    RenderSnippet() ChartSnippet
}
```

## `Render(w io.Writer) error`

The `Render(w io.Writer) error` function aims to generate chart to target `io.Writer`.  
Underlying, it depends on the `RenderContent() []byte` to generate the chart bytes streaming.

## `RenderContent() []byte`

The `RenderContent() []byte` uses templates to generate the chart bytes streaming.


## `RenderSnippet() ChartSnippet`

The `RenderSnippet() ChartSnippet` function can extract the element(chart container), the script
and the options from a chart.

!> It only works for Chart, Page is unsupported.

e.g.
> Full Code: [examples/renderer.go](https://github.com/go-echarts/examples/blob/master/examples/renderer.go)
```go
	bar := charts.NewBar()
	bar.SetGlobalOptions(charts.WithTitleOpts(opts.Title{
		Title:    "Bar chart for Snippets",
	}))

	bar.SetXAxis([]string{"Mon", "Tue", "Wed", "Thu", "Fri", "Sat", "Sun"}).
		AddSeries("Category A", generateBarItems()).
		AddSeries("Category B", generateBarItems())

	// pure extracted snippets
	chartSnippet := bar.RenderSnippet()

	tmpl := "{{.Element}} {{.Script}} {{.Option}}"
	t := template.New("snippet")
	t, err := t.Parse(tmpl)
	if err != nil {
		panic(err)
	}

	data := struct {
		Element template.HTML
		Script  template.HTML
		Option  template.HTML
	}{
		Element: template.HTML(chartSnippet.Element),
		Script:  template.HTML(chartSnippet.Script),
		Option:  template.HTML(chartSnippet.Option),
	}

	// rerender the snippets out
	err = t.Execute(os.Stdout, data)
	if err != nil {
		panic(err)
	}

```

## Template customization

The built-in renderers support per-chart and per-page template overrides without
changing the `Renderer` interface. Configure `opts.Initialization.Templates` for
a standalone chart, or call `page.SetTemplateOptions(...)` for a page.

`opts.TemplateOptions` provides:

- `Overrides`: Go HTML template definitions parsed after the built-in templates,
  in order. The last non-empty definition of a name wins.
- `Data`: application values available through `{{ renderValue "key" }}` in any
  template, including inside loops. An absent key returns `nil`; use `with` or
  `if` when a value is optional.

### Script and style attributes

`script_attributes` and `style_attributes` are empty by default. Override them
to add attributes without copying the chart initialization code or page styles:

```go
// nonce is generated by the application or its CSP middleware for this request.
templateOptions := &opts.TemplateOptions{
    Overrides: []string{`
        {{ define "script_attributes" }}{{ with renderValue "nonce" }} nonce="{{ . }}"{{ end }}{{ end }}
        {{ define "style_attributes" }}{{ with renderValue "nonce" }} nonce="{{ . }}"{{ end }}{{ end }}
    `},
    Data: map[string]interface{}{"nonce": nonce},
}

bar := charts.NewBar()
bar.SetGlobalOptions(charts.WithInitializationOpts(opts.Initialization{
    Templates: templateOptions,
}))
err := bar.Render(w)
```

The leading space before each attribute is intentional. Attribute values are
escaped by `html/template`; do not pass them through `safeHTML` or `safeJS`.
The script hook applies to both chart initialization scripts and generated
external JavaScript tags. The style hook applies to generated `<style>` tags.
Neither hook rewrites raw HTML supplied through `AddCustomizedHeaders`.

For a page:

```go
page := components.NewPage().
    SetTemplateOptions(templateOptions).
    AddCharts(bar, charts.NewLine())
err := page.Render(w)
```

A page uses its own templates and data for the entire output, including every
child chart. Child template configurations are ignored even when the page has
no template configuration, and are never modified. Rendering a child standalone
still uses that child's configuration.

### Replacing larger sections

Existing named templates can also be replaced:

| Name | Section |
| --- | --- |
| `header` | Page title and resource loading |
| `base_element` | Chart container |
| `base_script` | Chart initialization, events, and custom JavaScript |
| `base_option` | ECharts option output |
| `base` | Combined chart element and script |
| `chart` / `page` | Entire standalone chart or page document |

For example, replace the container while retaining the default chart script:

```go
templateOptions := &opts.TemplateOptions{
    Overrides: []string{`
        {{ define "base_element" }}
        <section class="custom-chart" id="{{ .ChartID }}"></section>
        {{ end }}
    `},
}
```

Supply sizing for `.custom-chart` in your stylesheet so ECharts can initialize
the container correctly. If replacing a script or style section, include the
attribute hooks yourself when needed; a full override replaces the built-in
markup, including its hooks.

`Render`, `RenderContent`, and chart `RenderSnippet` all use the configuration.
Snippets use `base_element`, `base_script`, and `base_option`, not the document's
`header`, `chart`, or `page` templates. Pages still do not support snippets.
With no overrides or data, the default output is unchanged.

### Security and lifecycle

- Overrides are trusted template code, not untrusted request input. The
  existing `safeHTML` and `safeJS` helpers bypass escaping and must be used with
  care. Invalid overrides panic, like the existing template parsing behavior.
- A CSP nonce must match the value in the HTTP response's CSP header. The
  application owns nonce generation and the policy; rendering does not set
  response headers or generate a nonce.
- Refresh request-specific `Data` for every request. Templates are rebuilt for
  each render, but the configuration remains on the chart or page. Prefer
  request-local charts and options; do not modify options or their maps
  concurrently with rendering. This feature does not make shared chart objects
  safe for concurrent rendering.
- A nonce on `<style>` does not authorize inline `style="..."` attributes.
  The default chart container uses inline sizing, so strict CSP may also require
  a custom container and external CSS. This feature alone does not guarantee
  compatibility with every CSP policy.

## Custom Renderer
You can implement the `Renderer` all by yourself, such as
[MyRender Example](https://github.com/go-echarts/examples/blob/master/examples/renderer.go).  
If you just want to use one of the `Renderer` functions, you can use th `BaseRender`. e.g.

> The `BaseRender` is a base Render with default implementations of Renderer.
> It helps you can only implement your own necessary functions of `Renderer`.

```go
type chartRender struct {
    BaseRender
	// chart instance
    c interface{}
    // before the pre-process functions for chart render, it should only call once to support multi renders
    before []func ()
}

```

!> You need run the `before` functions to make sure all the charts options set in place.
